## 2. 해결 설계

### O1. 릴리스 파생값 자동화 — `update:release-pins`

**목표 상태: 릴리스의 수동 지점이 32곳 → 2곳(버전 결정, CHANGELOG 산문)이 된다.**

수동 32곳의 내역(부록 F 실측)과 자동화 가능성:

| 기록 | 곳 | 자동화 |
| --- | --- | --- |
| 워크스페이스 package.json 버전 | 5 | ✅ 루트 버전에서 파생 |
| 워크스페이스 상호 참조 핀 | 6 | ✅ 동일 |
| `CROSS_REPOSITORY_STYLE_CONTRACT.json` 위성 버전 | 4 | ✅ 입력값(robotics 버전)에서 파생 |
| robotics tarball 참조 | 3 | ✅ vendor 디렉터리 스캔 |
| `ROBOTICS_EXTERNAL_SURFACE.json` 파생값(sha256 포함) | 10 | ✅ tarball에서 계산 |
| `vendor/README.md` 버전 표기 | 3 | ✅ 동일 |
| CHANGELOG | 1 | ❌ 사람의 산문 — 남긴다 |

구현 2개:

1. **`scripts/update-release-pins.mjs`** — 입력은 루트 버전과 robotics 버전
   둘뿐. 나머지 31곳(sha256 포함)을 전부 재계산해서 쓴다.
2. **`check:release-pins`** — 같은 계산을 읽기 전용으로 수행해 실제 파일과
   diff. 불일치 1곳이라도 있으면 실패. check:fast에 배선한다.
   → 손 동기화 실수가 "조용한 드리프트"에서 "CI 실패"로 바뀐다.

순서 제약 하나를 레시피에 명시한다: sha256은 tarball에서 계산하므로
**robotics tgz가 vendor에 먼저 들어온 뒤** 스크립트를 돌린다.

### O2. 핀 정렬 — "침묵 불가"의 기계화

**목표 상태: 핀 격차는 허용되지만, 기록 없는 격차는 CI가 거부한다.**

R4-2의 계약("스킵은 가능하되 침묵은 불가")을 그대로 두고 강제 장치만 단다:

1. **`report:satellite-pins`** — 활성 위성 4개의 package.json을 GitHub
   raw에서 읽어 `docs/references/SATELLITE_PIN_REPORT.json` + `.md`를
   생성한다. 내용: 위성별 LDS 핀, 현행 라인, 격차, 마지막 갱신일.
2. **`check:satellite-pins`** — 리포트가 최신 릴리스 태그보다 오래됐으면
   실패. **격차 자체는 실패 사유가 아니다** — 격차를 알고도 스킵하는 건
   소유자 권한이고, 모르는 채 방치되는 것만 막는다.

slides-ui rc.4 → rc.69.x 정렬 실행은 이 계획의 범위가 아니라 별도 작업이다.
리포트가 생기면 그 격차가 분기마다 눈앞에 놓이므로, 정렬 시점 결정은
데이터를 보고 한다.

### O3. main 상시 초록 — 빨간불의 의미 회복

**목표 상태: main의 빨간불 = 항상 진짜 고장. "정상인 빨간불"은 0개.**

원인은 배선 하나다: `check:release-immutability`가 check:fast(검사 50개)에
포함되어 있다. 이 검사의 보호 시점은 **퍼블리시 순간**인데(같은 버전 재출시
방지), 퍼블리시는 릴리스 워크플로를 통해서만 일어나고 그 워크플로는 이미
전용 단계로 이 검사를 돈다(`release-packages.yml` 45행,
`check:release-immutability -- --tag`).

따라서 수정은 삭제가 아니라 **배선 이동**이다:

> **실행 시 정정(§7.1)**: 아래 1번은 실행 중에 더 정확한 형태로 바뀌었다.
> 스크립트를 목록에서 빼는 대신 **태그 동일성 검사만 `--tag` 안으로** 옮겼다.
> `check:fast`에는 지금도 `check:release-immutability`가 들어 있으며, 그것이
> 의도된 최종 상태다 — 버전 일관성 검사는 상시 유효하기 때문이다.

1. ~~check:fast 목록에서 `check:release-immutability`를 뺀다.~~ → §7.1 참조
2. 릴리스 워크플로의 전용 단계(45행)는 그대로 둔다 — 보호력 손실 0.
3. 결과: 태그 사이 커밋에서 main CI가 초록이 되고, 빨간불은 실고장만
   가리킨다.

부수 효과: 선행 문서와 메모리에 기록된 "main은 릴리스 사이에 빨간불이
설계"라는 서술이 무효가 되므로, 해당 문서들을 같은 커밋에서 갱신한다.

### O4. 버스 팩터 완화 — 이관 가능성의 검증

**목표 상태: 문서만 읽은 사람이 정의된 작업을 질문 없이 완수한다.**

코드로 풀 수 없는 유일한 항목. 할 수 있는 것은 둘이다:

1. **`docs/OPERATIONS.md` 신설** — 단일 진입 운영 가이드. 내용은 세 가지로
   제한한다: ① 릴리스 레시피 전문(O1 이후 기준: 버전 결정 → robotics tgz →
   `update:release-pins` → CHANGELOG → 태그) ② 위성 지도와 각 계약의 위치
   ③ 정상 상태의 정의(O3 이후 "정상인 빨간불"은 없다 — 빨간불이면 고장이다).
2. **이관 시험** — 동료 1인이 이 문서와 레포 README만으로 (a) lds-motion
   퀵스타트 완주 (b) 슬라이드 텍스트 수정 1건을 수행한다. 질문이 발생한
   지점을 전부 기록하고, 각각을 문서 구멍으로 취급해 메운다. 질문 0으로
   완주될 때까지가 시험이다.

이 시험은 "배포 검증"이 아니라 **"체계가 소유자 없이 전달되는지"의
검증**이다. lds-motion 콜드 클론 → 렌더는 2026-08-16 기계 검증을 통과했고,
남은 것은 사람 축뿐이다.

## 3. 실행 순서와 게이트

의존이 얇은 것부터. 각 단계는 독립 커밋·독립 롤백.

```text
Phase O-A  O3 배선 이동          작게 시작 — diff 2줄, 즉시 신호 회복
Phase O-B  O1 파생값 자동화       가장 큰 감량 — 32 → 2
Phase O-C  O2 핀 리포트           O1의 계산 로직 일부를 재사용
상시       O4 운영 가이드·이관 시험  O-A~C 완료 후가 적기 (레시피가 확정된 뒤)
```

게이트: O-B는 **다음 릴리스에서 스크립트 산출과 손 계산이 일치하는지** 1회
병행 검증 후에 손 절차를 폐기한다. O-A는 릴리스 워크플로의 전용 단계가
실제로 실패를 잡는지(의도적으로 버전 미범프 상태로 드라이런) 확인 후 병합.

## 7. 실행 기록 (2026-08-16)

### 7.1 O-A — 태그 동일성 검사의 배선 이동

계획은 "check:fast에서 `check:release-immutability`를 뺀다"였으나, 실행
중에 그 스크립트가 **성격이 다른 두 가지**를 하고 있음이 드러났다:

| 검사 | 성격 | 처리 |
| --- | --- | --- |
| 버전 일관성 (락파일·CHANGELOG·패키지 버전 일치) | 상시 유효, 언제나 만족 가능 | check:fast에 **남김** |
| 태그 동일성 (태그 == HEAD) | 태그 이후 커밋에서 구조적으로 실패 | `--tag`로만 실행 |

그래서 스크립트를 통째로 빼지 않고 후자만 `--tag` 안으로 옮겼다. 계획보다
보호력이 더 남는다 — 버전 일관성은 계속 매 커밋 검사된다.

**게이트 결과**(§3이 요구한 드라이런): 저장소가 마침 "태그 이후 미범프"
상태였으므로 그대로 시험이 됐다.

- 상시 모드 → 통과 (`0.1.0-rc.69.18 -> lds-v0.1.0-rc.69.18 -> HEAD`)
- `--tag` 모드 → **정확히 실패**: `lds-v0.1.0-rc.69.18 already identifies
  4a19cf26…; HEAD b359d36c… must bump the package-set version`
- `check:fast` 50개 전체 → **exit 0** (main 초록 회복 실측)

### 7.2 O-B — `update:release-pins` / `check:release-pins`

`scripts/update-release-pins.mjs` 하나가 쓰기와 검산을 겸한다(`--check`).
입력은 LDS 버전과 robotics 버전 둘뿐이고, 파생 31곳을 계산한다.

**자동화하지 않기로 한 것**: `CROSS_REPOSITORY_STYLE_CONTRACT.json`의
`profiles.*.packageDependencies`. 실행 중 확인한 바, 이 값들은 우리가
정하는 값이 아니라 **위성 저장소를 관측한 사실**이다. 덮어쓰면 계약이 실제와
달라진다. 이 축은 O-C가 맡는다.

검증 3종:

- 양성 — 현재 상태에서 `--check` 통과 (31곳 일치)
- 음성 — `--check --lds 0.1.0-rc.69.99`로 LDS 파생 **10건 드리프트 탐지**
- 멱등 — 쓰기 모드 실행 후 `git status` 변경 0건 (JSON 서식도 보존)

### 7.3 O-C — 위성 핀 리포트

`scripts/report-satellite-pins.mjs`가 위성 4개의 package.json을 읽어
`docs/references/SATELLITE_PIN_REPORT.{json,md}`를 생성한다. `--check`는
네트워크 없이 **신선도만** 본다(리포트의 releaseVersion ≠ 현재 버전이면 실패).
음성 시험으로 낡은 리포트가 실제로 차단되는 것을 확인했다.

첫 실행이 곧바로 사실 3건을 드러냈다 — 리포트를 만든 이유 그 자체다:

| 발견 | 내용 |
| --- | --- |
| **robotics-ui도 rc.4에 핀** | 뒤처진 것이 slides-ui만이라는 기존 인식은 틀렸다. 가장 성숙한 위성도 65버전 뒤에 있다. 릴리스 동반은 *LDS가 robotics를 vendoring하는 방향*이지 robotics가 LDS를 따라가는 것이 아니었다 |
| **slides-ui는 theme만 peer 선언 누락** | core·product는 Phase 3 계약대로 `peerDependencies`인데 theme만 vendored tgz뿐이다. 소비자에게 theme 필요가 고지되지 않는다 |
| **motion은 `dependencies`에 `file:`** | T3 함정 상태. 지금은 clone 소비라 동작하지만 퍼블리시하는 순간 깨진다 |

이 3건은 발견 시점에는 기록만 했다. **같은 날 소유자 지시로 전부 해소했다 —
§7.6.**

스크립트 자체에서 버그 1건을 잡았다: LDS 레이어를 이름으로만 모아 뒤 섹션이
앞을 덮어써서, slides-ui의 `peerDependencies` 선언이 리포트에서 사라졌다.
섹션별로 모으도록 고쳤다. 같은 이유로 `vendored-only`와 `no-lds-pin`을
분리했다 — 전자는 T3 함정, 후자는 LDS 미사용으로 필요한 조치가 다르다.

### 7.4 O4 — 운영 가이드

[`OPERATIONS.md`](OPERATIONS.md)를 신설했다. 릴리스 레시피(O-B 이후 기준),
위성 생멸 규칙, 정상 상태의 정의, 자주 쓰는 명령. **이관 시험은 사람 축이라
미실시**이며, 문서 §6이 그 사실을 스스로 밝히고 있다.

## 7.6 후속 — 핀 격차 해소 (같은 날 실행)

§7.3이 "기록만 하고 고치지 않는다"고 남긴 3건을 소유자 지시로 전부 해소했다.

| 위성 | 조치 | 결과 |
| --- | --- | --- |
| robotics-ui | `dependencies` → `peerDependencies`, rc.4 → rc.69.18 | **rc.19** |
| slides-ui | vendored·peer 전부 rc.69.18, theme peer 추가 | **alpha.4** |
| motion | `private: true` 선언, publishConfig 제거, rc.69.18 정렬 | **alpha.4** |

세 가지가 드러났다:

1. **robotics의 `dependencies` 선언이 디자인 시스템을 두 벌 설치시키고
   있었다** — 워크스페이스의 rc.69.18 옆에 레지스트리에서 내려온 rc.4가
   중첩 설치됐다. peer 선언이 이를 한 벌로 접는다.
2. **rc.4에 묶여 있던 원인은 관리 소홀이 아니라 레지스트리에 rc.69.x가
   없었던 것이다.** 2026-08-16 첫 퍼블리시 성공이 이 정렬의 선행 조건이었다.
3. **65버전 격차에 실제 비호환은 0이었다.** slides-ui QA 2건 통과, motion
   렌더는 바이트까지 동일(sha256 `453a93d8a374e717…`). 격차는 비호환이
   아니라 기록되지 않은 상태였다.

motion은 당초 "peerDependencies로 전환"을 계획했으나 실물을 보고 뒤집었다.
`main`·`exports`·`files`가 없는 애플리케이션이라 peer 전환은 레지스트리 인증
없이 끝나던 clone 설치를 깨뜨린다. `private: true`가 T3를 구조적으로 없애는
동시에 그 이점을 지킨다.

### 7.6.1 후속 — peer를 정확히 핀한 것 자체가 결함이었다

위 조치로 robotics를 peer 선언으로 바꿨지만 **정확한 버전**을 유지했다.
다음 릴리스(rc.69.19)를 준비하면서 그것이 문제를 옮겼을 뿐임이 드러났다.

- 호스트가 rc.69.19로 올라가자 robotics의 정확한 peer(rc.69.18)를 맞추려고
  npm이 다시 중첩 사본을 설치하려 했다(`ERESOLVE`, 그리고 레지스트리 접근을
  요구해 401).
- 그렇다고 robotics가 rc.69.19를 핀할 수도 없다. **아직 퍼블리시되지 않은
  버전은 레지스트리에서 설치할 수 없다.** 즉 정확한 peer는 구조적으로 항상
  한 릴리스 뒤처지고, 뒤처지는 순간 중첩이 발동한다. 자기 꼬리를 무는 구조다.

계약이 값을 하나만 갖고 있던 것이 원인이었다. 서로 다른 두 질문에 같은 값이
답하고 있었다:

| 필드 | 답하는 질문 | 형태 |
| --- | --- | --- |
| `version` | 무엇으로 **검증**했나 (재현성) | 정확한 버전 |
| `declaredRange` | 무엇과 **함께 쓸 수 있나** (호환성) | 범위 |

`declaredRange`를 신설하고 peerDependencies에만 허용했다. 검증한 버전을
포함하지 않는 범위는 거부한다 — 그러면 계약이 "확인한 적 없는 조합"을
호환된다고 주장하게 된다. 검사 3곳(`check:conformance`의 두 규칙,
`check-cross-repository-style-contract.mjs`)을 모두 이 구분에 맞췄다.

핀 리포트에서도 같은 구분이 필요했다. `devDependencies`는 위성 자신의
개발용이고 마찬가지로 퍼블리시되지 않은 버전을 설치할 수 없으므로 영원히
한 릴리스 뒤처진다 — 격차로 세면 신호가 죽는다. 판정은 소비자에게 하는
호환성 주장(`dependencies`·`peerDependencies`)만 본다.

`update:release-pins`에서도 같은 종류의 순환을 하나 더 찾았다. 설치는 루트
package.json이 새 tgz 경로를 가리켜야 하는데, 그 경로를 쓰는 것이 이
스크립트다. 2단계 실행(1차는 경로·버전, `npm install` 후 2차에서 해시)으로
풀고, 2차를 잊어도 `check:release-pins`가 막게 했다.

## 7.7 O4 이관 시험 (실시)

문맥이 전혀 없는 독자 둘로 시험했다. 결과와 메운 구멍은
[`OPERATIONS.md`](OPERATIONS.md) §7에 기록했다. 요지:

- **신입 시험(lds-motion)**: 완주. 그러나 소스 5개를 열었고 2개는 문서에
  답이 없어서였다. 최대 구멍은 **슬라이드 목록·prop의 출처가 어느 문서에도
  없던 것**(실제 출처는 `src/types/lds-slides-ui.d.ts`).
- **인계자 시험(릴리스)**: 1단계에서 중단. **robotics 저장소 위치와 절차가
  어느 문서에도 없었다.**

두 시험이 공통으로 가리킨 실패 양식은 "틀린 문서"가 아니라 **"Status:
Current를 단 낡은 문서"**였다. SKILL.md는 README보다 뒤처져 있었고,
HANDOFF.md는 한 달 전 상태를 현재 상태 권위로 주장하고 있었다. 그래서
현재 상태의 권위를 `docs/README.md`의 표 하나로 모으고, 손으로 갱신하던
숫자는 스크립트 산출물로 대체했다.

O4가 완료 조건으로 삼은 "질문 0으로 완주"는 아직 아니다 — 메운 문서로
다시 시험해야 확인된다. 다만 **버스 팩터 1의 실제 내용이 무엇인지는 이제
목록으로 존재한다.**
